## 分级验证与完成标准

### 1. 文档与只读任务

- 只读审计交付证据和建议，不触发产品发布。
- 文档修改验证链接、归档完整性、当前版本、规则一致性及 Git 差异。不得把历史通过结论写成本轮新验证。

### 2. 模块修改与局部验证

- 开发过程中优先运行表中的相关测试；修复其暴露的本次问题后复跑受影响项。
- 真实页面解析、点击、价格、规格或状态流转改动，增加对应真实页面/样本验证。仅修复局部问题可以按局部验收交付，但必须列出未完成的整体验收。
- Agent 仅有本地代码变更时运行相关测试并说明重启要求；修改桥接或扩展后仍需扩展发布构建。

### 3. 产品发布与端到端验收

- 网页、扩展或运费规则代码交付前执行 `powershell -ExecutionPolicy Bypass -File tools\build-release.ps1`。该脚本目前统一构建网页、扩展 ZIP 和裁图 ZIP，**没有按模块打包开关**；本次只优化文档，不增加或假定已有该功能。
- `tools/verify-project.ps1` 与 `npm.cmd test` 当前覆盖不完全相同：前者有额外语法、网页哈希和备份数量检查，但未列入 1688 core、1688 extension、sourcing-agent-1688、pinduoduo-agent 四组测试。因此不能把发布构建通过视为完整 `npm.cmd test` 通过。
- 完整版本发布运行 `npm.cmd test` 和发布构建各一次；在最终改动后已完成的同一检查无需无理由重复。局部交付按相关测试加必要发布构建执行，并明确验证范围。未来统一测试入口需作为单独代码改动验证。
- 核对扩展 ZIP 的版本、文件集合和源码一致性。生成的其他产物仅在确有必要内容变化时纳入本次提交。
- 真实浏览器按 [验收清单](../真实浏览器验收清单.md) 选相关章节；跨模块或完整能力交付运行相关端到端流程。当前 1688 MVP 6.0 的完整验收仍需单件、三件及 20 件证据，不能借分级验收把未测项标为通过。
- 完成时区分“实现/自动验证/打包完成”“真实验收通过”“已安装/已部署”。遇到用户登录、平台验证或缺少人工样本等实际阻断，保留具体原因和下一步。
